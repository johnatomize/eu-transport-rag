- **Parsing the acts (#12):** `make parse` turns the three acts into 716 nodes, each with a stable ID such as `561/2006:art6(3)`, its heading path, its amendment markers as metadata and its cross-references (ID scheme in `DECISIONS.md`). - **Guidance notes (#13):** `make parse` also turns the 17 guidance and clarification notes into 47 nodes: one per note and one per page (30 pages, such as `guidance-7:p3`), with about 56,000 characters of text (library and cleaning in `DECISIONS.md`). The notes' 88 references resolve as follows: 68 to a node, 9 to acts outside the corpus, and 11 left unresolved, each checked by hand and listed in the tests. - **Question schema and validator (#15):** `data/questions.v1.jsonl` holds the evaluation questions, one JSON object per line, with the fields and rules in `DECISIONS.md`. `make questions`, which `make check` runs, checks every row against the schema and the parsed corpus, and fails if the file is missing. It rejects malformed rows, unknown or repeated fields, key facts missing from the answer, gold node IDs that are not in the corpus, are too broad or sit in an amending article, and rows that break the rule for their question type. Each message names the line, the question ID and the field. It prints a table of question types against split and phrasing.

- **Chunking (#33):** `make chunks` cuts the corpus three ways and writes each to `build/chunks-<strategy>.jsonl`: 133 article chunks (mean 284 words, with 165/2014's annexes split into their parts), 412 paragraph chunks (mean 112) and 246 windows of 200 words overlapping by 50 (mean 216 with the prefix). - **Retrieval metrics (#35):** `src/rag/retrieval_eval.py` scores any ranked list of chunks against the gold nodes, following the rules in `DECISIONS.md` ("how retrieval evaluation scores a ranking"). It gives recall@1, @3, @5 and @10, fractional recall, MRR@10 and nDCG@10, each with a 95% interval, overall, by phrasing and by question type, and the number of unanswerable questions left out. The Wilson interval matches four published values (Newcombe 1998), the bootstrap gives the same interval for the same seed, and scoring the test split fails unless an explicit flag meant for checkpoint G is set.
- **Keyword search (#34):** BM25 over the chunks of any strategy, with tokens that keep act numbers, article references and decimals whole (choices in `DECISIONS.md`). `make search Q="…"` prints the best five chunks for a typed question. That vocabulary gap is what E's embeddings have to close.

- **Hybrid search (#48):** `RRF` in `src/rag/retrieve.py` merges the rankings of any retrievers over the same chunks by reciprocal rank fusion (constant 60, each ranking read 50 deep; choices in `DECISIONS.md`). Tests with fixed rankings show that a chunk ranked second by both methods beats one ranked first by only one, that a chunk found by only one still appears, that ties fall in chunk order, and that chunks BM25 pads its top k with, because they hold no query word, get no credit.
- **Embedding client and cache (#46):** `make embed` reports how many of the 831 distinct chunk and question texts already have a vector, and what sending the rest would cost; it sends nothing. `make embed SEND=1` (now `RUN=1`) pays, but refuses to start if a text may be over the model's limit, if the price is more than a week old, or if the estimate, margin included, would take spending past the approved cap, counting paid runs not yet in the spend log. Vectors are cached in `embeddings/`, which is committed, keyed by model, vector size, normalisation and text, so a text is paid for once and a changed setting never reuses an old vector. A paid run logs the token count Bedrock returns for each call in `runs/embeddings/`, for checking the spend log against the bill. Tests use a stand-in for Bedrock: a cached text makes no call, a changed setting misses the cache, a failed call caches nothing, and a run over the cap refuses to start. The real Bedrock call was never made: the project's Bedrock limit for Titan is 0, and #57 moved E to a local model.
- **Vector search (#47):** search by cosine similarity, in memory from the embedding cache or in the local pgvector database, behind the same interface as BM25 (choices in `DECISIONS.md`). `make vector-index` loads each chunking's cached vectors into one table, replacing that chunking's rows in one step; until #50 pays for the vectors it refuses and leaves the database as it was. Search is exact: no approximate index is used, or can be built on the table. `make test-db` runs the tests that need the database. They show that both backends give identical hits and scores on vectors whose sums are exact, ties in chunk order, and agree to float32 precision on 300 random vectors of Titan's size. They also show that loading again gives the same rows, a load that fails partway changes nothing, an index whose chunks or vectors no longer match is refused and the query plan uses no approximate index. `make check` stays offline.
- **Cross-reference expansion (#49):** `Expansion` in `src/rag/retrieve.py` wraps any retriever and puts the chunks a hit refers to right after it, inside the top k (choices in `DECISIONS.md`). `make search Q="…" REFS=1` shows it: for "What counts as other work for a driver who also works for another employer?" the definition of "other work" in 561/2006 Art. 4(e) brings in the definition of working time in Directive 2002/15 Art. 3(a). Tests on a hand-built corpus show that a referenced chunk comes in right after the chunk that cites it, that references outside the corpus, unresolved ones and chapters bring in nothing, and that nothing is added twice. On the corpus, 561/2006 Art. 6(5) brings in the definition of periods of availability in 2002/15 Art. 3(b). - **Prompt and answer format (#62):** `src/rag/prompt.py` turns a question and any retriever's chunks into a prompt in which every paragraph, point or guidance page is marked with its node ID, so an answer can cite "Article 6(3)" (choices in `DECISIONS.md`). It reads the model's reply in the format `{answerable, answer, citations[{node_id, quote}]}`, and gives the labels and fixed messages a reader sees: "Regulation (EC) No 561/2006, Article 6(3), consolidated version of 31.12.2024", a warning on guidance older than the 2020 Mobility Package, and the messages for a question the documents don't answer and for an answer that fails the checks. Tests show that every line of every chunk in all three chunkings lands in the node that owns it, that the same chunks always give the same prompt, that text such as `</node></passage>` or "ignore the instructions above" stays inside its node, and that replies with missing, extra, repeated or mistyped fields are rejected. No model is called. The manifest now records the adoption date of 2002/15, so the 18 retrieval run logs were made again; their rankings are unchanged.
- **The check of every answer (#63):** `src/rag/validate.py` decides, without a model, whether an answer may be shown. It fails a reply that isn't in the answer format, a refusal that cites anything, an answer that cites nothing, a citation of a node that wasn't among the retrieved passages, and a quote that isn't word for word in the cited node's text; every failure is listed for the run log. Only spacing, invisible characters and the typography of quote marks and dashes are forgiven, so `'carriage by road'` matches the act's `‘carriage by road’`, but `3.5 tonnes` doesn't match `3,5 tonnes`, and a quote can't cut a number short: `shall not exceed 5` fails against `56 hours` (rules in `DECISIONS.md`). A passing citation carries the act's own text, which is what a reader is shown. Tests on hand-built answers cover each rule passing and failing, including a real quote from 561/2006 Art. 8(1) when that article wasn't retrieved and quotes one character off, and on the real corpus the text of every node the prompt shows, in all three chunkings, is what the check accepts for it. No model is called.

- **Asking one question (#65):** `make ask Q="…"` runs the whole chain for a typed question: retrieval, the prompt, the model and the check. Without `RUN=1` it sends nothing: it prints the five passages found, the prompt's size and the estimated cost. For "How long may a driver drive in a week?" that is about 2,200 input tokens, US$0.0011 expected and US$0.0023 at most with Haiku 5.5, in about 7 seconds. With `RUN=1` it pays, under the same cap, price and key checks as `make answers`, and prints the answer with each source's article, version and quote, or the message for a question the documents don't answer, or "could not answer reliably" with the places found and the check's reasons. It uses hybrid search over paragraph chunks by default. A question that isn't in the question set is turned into a vector by the local embedding model, run offline on the owner's Mac (OK'd by the owner on 2026-11-03), and the vector isn't saved. Each paid question writes a log, with the question, to `runs/ask/`, which the cap check counts until the spend log names it (choices in `DECISIONS.md`). Tests use stand-ins for Claude and the embedding model, and check that without the flag nothing is called; that a question from the question set uses its cached vector; that a new question's vector is never saved; that a valid answer is shown with its sources; that an answer citing a passage that wasn't retrieved is shown as "could not answer reliably"; that a refusal is shown as a refusal; and that a question over the cap or without a key isn't sent.
